# Codexレビュー依頼：スワイプ→インク→名前表示の演出フロー再設計

作成: 2026-07-16（Claude セッションからの相談文書）
目的: **下記の設計方針で実装してよいか、フロー分離作業との整合を含めてレビューしてほしい。**
まだ実装していない。設計合意が取れてから着手する。

---

## 1. 課題

スワイプ直後にインク着弾演出が始まるが、名前入力はその後（数十秒かかる）。
参加者が「自分のスワイプが大画面のどこに反映されたのか」を見失う。

優先順位:
1. 自分のスワイプの反映位置が分かること
2. 操作直後に反応が返ること
3. 名前入力を焦らせないこと
4. インク演出の気持ちよさを損なわないこと

## 2. 現状実装の確認結果（レビューの前提）

すでに「二段階」の仕組みが本番にある:

- スワイプ確定: `publishSwipeComplete`（`src/firebase-bridge.js:238`）がカウントを
  increment で確定。大画面 `demo_v2.html` は `spawnImpact`（:2044 付近）で
  **匿名のインク着弾**を即時に打つ。
- 位置は決定的: `layerIndex = (swipeCount - 1) % 18`（TOTAL=18窓）。
  スマホ側は `completedSwipeCount` を保持しているので、
  **スワイプ確定の瞬間に自分の窓位置をクライアント側だけで計算できる**。
- 名前確定: `publishNameAnnouncement`（`firebase-bridge.js:509`）が
  `swipeCount` 付きで nameShouts に飛び、大画面は `relightParticipation`
  （`demo_v2.html:2021`）で**同じ窓を再点灯（linked アウトライン 2.6s）＋名前表示（2.8s）**。
- 入力欄ヘルプ文も「名前を追加すると、同じインクが光ります」とこの二段階前提。

## 3. 提案する設計：「着弾」と「名入れ」の二拍構成 ＋ スマホがミニマップを持つ

設計の軸: **名前入力中、参加者の目はスマホにある**（大画面を見られない）。
→ 位置の記憶は大画面に保留させず、入力中ずっと見ているスマホに持たせる。

### 1拍目＝着弾（スワイプ直後 0〜1s）
- 大画面: 現行どおり匿名インク即着弾（変更なし）。
- スマホ: カウント確定と同時に**着弾位置カード**を表示。
  18窓の簡略ミニマップに自分の窓をハイライト＋「左上・3番目の窓に着弾しました」。
  `(completedSwipeCount - 1) % 18` から描くだけなので**大画面側の変更ゼロ**。

### 入力中（10〜60s）
- スマホ: ミニマップを入力欄の上に小さく残す（「この窓に名前が灯ります」）。
  カウントダウン等の焦らせる表示は置かない。
- 大画面: 何も保留しない。他参加者の着弾は通常どおり。

### 2拍目＝名入れ（入力確定後 0〜3s）
- スマホ: 確定タップ →「インクに名前を注いでいます…」（書き込み待ちを演出で包む）
  → `publishNameAnnouncement` の **完了を await してから**「上を見て！あなたの窓が光ります」。
  通信完了後に見上げさせるので「見上げたのに何も起きない」事故が構造的に起きない。
- 大画面: 名前表示の直前に**ビーコン**（窓を起点とする同心円リップル1〜2発、600ms）を
  先行させ視線を誘導 → 既存 linked アウトライン再点灯 → 名前せり上がり。
  linked 時の名前表示は 2.8s → 4s 程度に延長したい（感情のピークのため）。

## 4. 却下した代替案（理由つき）

- **案A: 目印だけ出して、入力完了後にインク着弾**
  最大のペイオフが数十秒先送りで「操作直後の反応」が死ぬ。入力中は誰も大画面を
  見ていない。複数人同時入力で保留マーカーが並ぶ・離脱時のタイムアウト・
  18窓周期で N+18 人目の着弾と衝突、と共有画面に個人の保留状態を持たせる設計は破綻しやすい。
- **案B: 「あなた」等の仮ラベルで先に演出→後で差し替え**
  名前表示は 2.8s で消えるのに入力は数十秒 → 「表示中の差し替え」は実際には起こらず
  必ず2回目の表示になる＝現行 relight と同じ。公共画面の「あなた」は誰のことか不明
  （同時入力3人なら「あなた」が3つ）。本名が"訂正"として届き、リビールの感動が薄れる。
- **案C: 名前を先に聞く（スライダーと同画面に任意入力）**
  単一クライマックスになる唯一の案だが、マジックモーメント前の摩擦で参加カウント前の
  離脱リスクが上がる。参加数最大化の現行方針とは相性が悪いので不採用。

## 5. Codex に判断してほしい点

1. **フロー分離との整合**: 分離後の participant / supporter 各フローで、
   ミニマップ挿入位置（スワイプ完了直後のステップと名前入力ステップ）は
   現在の Codex 側の構成と衝突しないか。ステップ構成が変わる予定があれば教えてほしい。
2. **`swipeCount` の信頼性**: 高負荷時（>5人/秒）に increment 確定が遅延した場合、
   スマホが計算する窓位置と大画面の実着弾位置がズレる余地はないか。
   （現行 relight も同じ `swipeCount` を使うので既存リスクと同等という理解でよいか）
3. **大画面側の追加**: ビーコン演出と linked 時の名前表示延長（2.8s→4s）は
   `demo_v2.html` に入れる想定。完成映像（celebration）・名前ロール等との
   干渉で気をつける点はあるか。
4. **「上を見て」文言の i18n**: UI_TEXT ja/en 両対応が必須という理解でよいか。
5. **実装の分担**: スマホ側（ミニマップ＋確定後キュー）と大画面側（ビーコン）を
   分けて進められる。どちらを Codex が持つか希望はあるか。
